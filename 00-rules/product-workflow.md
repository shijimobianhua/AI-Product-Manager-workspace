# 产品工作流与人机分工

原始输入 → 产品认知与规划 → 需求池 → 单需求定义 → 原型与PRD → 版本承诺 → 开发与验证 → 交付/发布 → 上线或实际使用验证 → 反馈与复盘。

| 阶段 | AI可以做什么 | 人需要决定什么 | 主要产物 |
| --- | --- | --- | --- |
| 输入 | 整理、提取、标来源与疑问 | 材料权限、实际背景 | SRC来源登记 |
| 产品和规划 | 分析问题、依赖、方案差异 | 价值取舍与边界 | 产品事实、规划和决策 |
| 定义与评审 | 写草稿、指出冲突、补异常与验收 | 范围和批准 | 需求工作包及评审证据 |
| 版本 | 梳理依赖和验证条件 | 做哪几个、何时承诺 | scope和实施计划 |
| 开发验证 | 在授权内改代码、跑检查、保管版本 | 新增风险、范围变更与验收 | 提交、测试和保管收据 |
| 发布交付 | 准备包、执行已批准动作、核对结果 | 具体生产发布与数据处置 | 产物、执行与部署记录 |
| 反馈 | 对照目标整理结果与新问题 | 目标是否达成、下一轮优先级 | 复盘及新的候选输入 |

资料先登记，结论分已观察、推断、待确认、未覆盖。阶段结论先取得负责人的确认，再写入正式事实或推进状态。当前明确授权范围内持续完成必要、可逆、可验证的工作，不对同一范围反复索要许可；新的生产发布、付费、隐私外传、有损数据或范围变更不可借用旧授权。

一次需求能独立定义、开发和验收；多个需求之间的共用内容放规划，单需求细节放工作包。范围变更后同步唯一PRD、实施和验收引用，不用聊天里的新说法悄悄替换既有批准。

执行者同步维护实际记录：没有运行的测试写未执行，失败记录保留，未知外部状态先核对原任务。使用者的正式状态和部署表目前不由模板自动改变。
